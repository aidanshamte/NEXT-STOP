# Physical-device acceptance: first milestone

**Milestone:** a verified student and an approved driver, using installed apps on separate networks, exchange a real pickup request and genuine shuttle location through the Azure-hosted backend with persistent accounts.

Run this with two physical phones and installed `preview` builds (PHONE-INSTALL.md, "Hosted pilot build"), **not** Expo Go, a QR code, a simulator or the web build. Mark an item passed only after you observe it. Record the date, phone models, OS versions, app build id and the API `/health` `release` value in VALIDATION.md.

Safety: never operate the app while driving. Use a passenger tester or a parked vehicle for driver actions.

## Before you start

- [ ] `curl https://<host>/health` returns `"ok":true` with the expected `release`.
- [ ] An administrator account exists (DEPLOY-AZURE.md step 7). Stops are added with real coordinates.
- [ ] Fairfield: under **Setup → Suggested boarding points**, approve the suggestions you have checked (FAIRFIELD-STOPS.md), and pin the two Block walkways on site with **Set boarding point**. Under **Routes and stops → Shuttle routes**, assign the test shuttle a route. Only confirmed stops can be requested.
- [ ] Both phones run the version 0.5.0 preview APK (Settings → Apps → NEXT STOP shows 0.5.0). Version 0.4.0 lacks the camera scanner and photo picker.
- [ ] Phone A (driver) is on **cellular data only** (Wi-Fi off). Phone B (student) is on a **different** Wi-Fi network, or on a different carrier.

## Arrival estimate accuracy (real service only)

Estimates appear only after a shuttle with an assigned route has passed confirmed stops at least three times per segment. Browser tests with supplied coordinates prove the logic, not accuracy. Do not describe estimates as accurate until this section passes.

1. Run normal service for at least five days with the route assigned and GPS on.
2. Daily, open **Setup → Arrival estimate accuracy**. Every time the shuttle passes a confirmed stop, the app records the range it was showing for the next stops. It then records when the shuttle actually arrived.
3. Separately, a rider writes down, for at least 10 arrivals at different stops, the estimate shown ("4–6 min") and the clock time the shuttle actually stopped. This checks the app's own measurement.
4. Pass when there are at least 30 measured arrivals per route, at least 80% within the shown range, and the hand-written observations agree with the app's figures. Record the figures and date in VALIDATION.md. Below that, keep calling them estimates and report the measured rate.

## Record failures precisely

For any failure, note the phone model, OS version, permission state (Precise / Always), battery-saver setting, network, the time, and the last `GPS` timestamp the student saw. Server-side, run `sudo journalctl -u next-stop --since "<time>"` (the logs contain no personal data).

Passing this checklist shows the pilot path works on these devices. It does not prove behavior on every device, under heavy load, or after the OS stops the app in the background.
